Plain language

Privacy and the pilot gate

Short version: the desktop app has no network client, no analytics and no AI. Student records live in a file on the school's PC. The only copies are the ones the school makes.

What the desktop app stores

Everything sits in one folder on the machine where you installed it:

%APPDATA%\org.agentmark.hub\agent-mark-hub\
hub.db encrypted vault (AGMDB001), not a readable SQLite file
vault.json staff accounts + Argon2id-wrapped copies of the data key
backups\ full encrypted snapshots + signed manifests

The vault holds student names, class codes, scores, teacher comments, approvals, report payloads, and the school's signing key. It is encrypted at rest with XChaCha20-Poly1305. The random 256-bit data key is never written in plaintext: each staff account gets its own Argon2id-wrapped copy, and the printed recovery code gets another. The app locks after 15 minutes of inactivity or when you press Lock.

What leaves the device

Nothing. The application contains no HTTP client for student data, no relay account, no licence check and no crash reporting. You can unplug the network cable and every feature still works.

  • The installer may fetch Microsoft's WebView2 runtime if the PC has never had Edge. That request goes to Microsoft and contains no school data.
  • Backup files are written where you choose; if you copy one to a USB stick, that is your action, not the app's.
  • This website is static. It sets no cookies, loads no fonts or scripts from third parties, and includes no analytics.

No AI, by design

There is no model, no inference, no training set, no prompt and no API key. Comments come from a reviewed bank of sentences that a teacher chooses and edits. Averages are weighted arithmetic; grade bands are fixed thresholds; ranking is competition rank. Given the same scores, the same card comes out in ten years' time.

Backups are sealed

A backup is a full snapshot of the encrypted database, sealed with XChaCha20-Poly1305 and accompanied by a manifest containing the schema version, row counts, SHA-256, timestamp, and an Ed25519 signature. A restore drill decrypts the blob into a fresh in-memory database and compares the counts, digest and audit head — the drill must pass before real data can be enabled.

Honest limitation: while the app is unlocked, anyone at that Windows session can read the records. The protection is the lock screen, the staff account password, and the encrypted-at-rest vault — not a hardware token. A stolen whole folder is ciphertext plus password-wrapped keys, so the attacker must attack Argon2id; keep the recovery code offline and use a strong passphrase.

Signatures and audit

Locking a report re-hashes the exact payload and signs it with Ed25519. The signature is returned as AGM1:<report-id>:<sha256>:<signature> so it can travel with a printed card as a QR code later. The signing key lives inside the encrypted vault. Every action appends a row to an audit log where each row hashes the previous one; altering history breaks the chain.

Verify a build yourself

Two independent checks ship with the project — neither trusts the app's own UI.

1. Check the download

Get-FileHash .\Agent-Mark-Hub-0.2.0-x64-setup.exe -Algorithm SHA256

Compare with the value on the download page.

2. Check the vault, audit, reports and backups

The offline checker opens the encrypted vault with a staff password, re-computes the audit chain, verifies the Ed25519 signature of every locked report, and verifies every backup manifest, signature, decryption, row count and audit head:

python hub-desktop\tools\verify_db.py "%APPDATA%\org.agentmark.hub\agent-mark-hub" --user admin

It prompts for the password. Expected output ends with RESULT: PASS. The live database is opened read-only; the decrypted snapshot exists only in memory.

The pilot gate

Real student data is not allowed yet. The desktop and mobile technical core is implemented, but an independent security review must close the findings below, and the school authorization, DPA/DPIA and parent notice must be signed, before a school enters a real name.

Open items, stated plainly:

  • No independent security review yet. The engineering tests are green; that is not the same as an audit.
  • No code-signing certificate has been issued for the Windows installers yet, so SmartScreen warns on first run. The release pipeline now requires and verifies a signature; an unsigned internal pilot build is clearly marked.
  • The published APK is debug-signed. CI has a release-signing path once a keystore is configured, but that keystore is not yet held.
  • Retention/pruning is manual. Data-subject export, correction, deletion, offboarding purge, stale-backup warnings, and restore-to-a-new-PC are implemented and tested; the school still owns the retention schedule and physical backup destruction.
  • The school/legal pack (authorization, DPIA, DPA, notices, training) is not signed.

The threat model, the test strategy and the backup/restore runbook are maintained in the project repository alongside the source. The detailed gate is in docs/REAL_DATA_READINESS.md.

Mobile app

The mobile app is a separate, deliberately limited companion. It creates a passcode-protected AES-256-GCM store on the phone, locks after 5 minutes, and can export an encrypted .agmm file for import into the desktop hub. The transfer file uses a separate 12+ character passphrase; there is no cloud relay and no always-on sync. Losing the passcode loses the phone data, so keep an encrypted export. "Wipe this phone" destroys the local store.

Who is responsible

The school remains the data controller. Agent Mark is software installed on the school's own equipment; it does not operate a service that receives student records. Questions about a specific deployment should go to the school's data protection lead.
